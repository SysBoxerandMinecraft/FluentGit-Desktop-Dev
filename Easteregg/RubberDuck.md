
# 🦆 小黄鸭调试法 · Rubber Duck Debugging

> “鸭子不会写代码。但鸭子能让你自己写出代码。”
> “The duck cannot write code. But the duck makes you write the code yourself.”

英文版：[RubberDuck.en.md](./RubberDuck.en.md)

---

## 一、缘起

FluentGit 项目组的工位上，放着一只小黄鸭。

它可能是塑料的，可能是橡皮的，可能只是一个黄色的、圆圆的、看起来无害的东西。
**但它是这个项目里最沉默、最耐心、最贵的工程师。**

它不说话。
它不打断你。
它不在你讲到一半的时候说“我懂了”。

它只是看着你。

**然后你就自己发现问题了。**

---

## 二、什么是小黄鸭调试法

小黄鸭调试法（Rubber Duck Debugging）是一种**古老、免费、且被严重低估**的调试技术。

流程只有三步：

```text
1. 拿一只鸭子（或任何不会回嘴的东西）。
2. 把代码一行一行地讲给它听。
3. 讲到一半，你会突然说："等等，这里不对。"
```

**第三步是唯一重要的一步。**

前两步，只是为了让你走到第三步。

---

## 三、为什么鸭子有效

鸭子不会解决你的问题。
**鸭子解决的是另一个问题——你脑子里的噪音。**

当你向一个同事解释问题时，你的脑子会自动进行社会性加工：

- “这句话该不该说？”
- “他会不会觉得我很菜？”
- “我要不要先铺垫一下背景？”

这些加工，会**吃掉你 20% 的思考带宽**。

但鸭子不会。
**鸭子不需要你铺垫背景。鸭子不在乎你菜不菜。鸭子不会打断你。**

于是，你的全部认知资源，都被用来**理解问题本身**。

然后——你就会发现问题。

> 鸭子是**认知带宽回收器**。

---

## 四、鸭子的规格

在 FluentGit 项目组，鸭子有正式规格。

| 项目 | 规格 |
|---|---|
| 材质 | 塑料 / 橡胶 / 陶 / 纸板 / 屏幕上的 emoji，均可 |
| 颜色 | 黄色（强烈推荐），其它颜色需项目组批准 |
| 高度 | 6–12 cm |
| 嘴型 | 微笑 |
| 眼睛 | 越大越好（凝视感更强） |
| 位置 | 显示器右侧，约 30 cm 处 |
| 朝向 | 面向使用者 |
| 依赖性 | 无。鸭子不依赖任何 NuGet 包 |
| 命名 | **必须**有一个名字 |

### 关于命名

**鸭子必须有名字。**

不是“那个鸭子”，不是“小鸭子”，不是“黄色的那个”。
**是一个具体的名字。**

比如：

- `Duck`
- `Quack`
- `Ducky`
- `小黄`
- `鲁班`
- 或者任何你觉得顺口的

**有名字的鸭子，会显得它在听你说话。**
**没名字的鸭子，只是一个摆件。**

## 五、鸭子的日常使用

### 5.1 标准流程

```text
1. 遇到一个 Bug，超过 15 分钟没头绪。
2. 把鸭子转过来，面向你。
3. 开始说话：

   "鸭子，是这样的。这个函数接收一个 repo 路径。"
   "然后它调用 GitService.GetStatus。"
   "GetStatus 会执行 git status --porcelain。"
   "然后……"

   （停了 3 秒）

   "等等。"
   "我传的是 repo 的绝对路径。"
   "但 GitService 期待的是相对路径。"
   "所以它一直在拿错误的目录跑 git status。"

   （3 分钟之后，Bug 修好了）
```

**鸭子在整段过程里，一句话都没说。**

### 5.2 什么时候用鸭子

| 场景 | 是否适合用鸭子 |
|---|:---:|
| 一个 Bug 超过 15 分钟没头绪 | ✅ 强烈推荐 |
| 一个 Bug 已经花了 2 小时 | ✅ 必须用 |
| 一个 Bug 已经花了一整天 | ✅ 用鸭子之前，先睡一觉 |
| 你在写一个新功能，思路不清 | ✅ 推荐 |
| 你在改一段自己看不懂的代码 | ✅ 强烈推荐 |
| 你只是想在摸鱼时跟鸭子说说话 | ❌ 不行 |
| 你想让鸭子替你做 Code Review | ❌ 不行（它不会说话） |

### 5.3 什么时候不用鸭子

- **当鸭子已经不看你的时候。**（说明你已经讲了 20 分钟了）
- **当你想让鸭子替你道歉的时候。**（鸭子没有社交能力）
- **当你在一个公开会议上用鸭子的时候。**（除非全组都有一只）

## 六、鸭子的进阶用法

### 6.1 代码旁听（Code Walking）

不只是**说**，还要**走**。

```text
1. 打开代码。
2. 用鼠标光标，从第一行开始，一行一行往下走。
3. 每走到一行，就把这一行念给鸭子听。
4. 不要跳行。
5. 不要跳函数。
```

**第 4 步和第 5 步是最难做到的。**

因为当你**跳行**的时候，你就是在**跳过可能有问题的那一行**。

**鸭子不允许你跳。**

### 6.2 双向沟通（Pseudo Dialog）

有些项目组会把鸭子拟人化，进行“对话”。

```text
你：鸭子，为什么这段代码会崩？
鸭：（沉默）
你：是不是因为空引用？
鸭：（沉默）
你：不，不对。如果是空引用，前面那个 guard 会拦住。
鸭：（沉默）
你：那就是并发问题。
鸭：（沉默）
你：不，也不是。并发问题是间歇性的，这个是必现的。
鸭：（沉默）
你：啊。
```

**鸭子永远沉默。**
**但每一次沉默，都在把你推向答案。**

### 6.3 反向鸭子（Reverse Duck）

如果你已经对鸭子讲了 30 分钟，还没有头绪——
**换一只鸭子。**

不是换物理鸭子。是换一个**心理位置**：

- 站起来，走到房间另一头。
- 假装自己是**另一只鸭子**。
- 用完全相反的角度，重新讲一遍。

**同样的故事，不同的耳朵，会听到不同的问题。**

## 七、鸭子与功德

鸭子不产生功德。
**鸭子只产生——"原来是这样"的那一刻。**

但项目组仍然给鸭子相关的行为，做了分类：

| 行为 | 功德 |
|---|---:|
| 用鸭子解决了一个 Bug | +3 |
| 用鸭子 15 分钟解决了 3 小时没解决的问题 | +20 |
| 用鸭子的时候，鸭子倒了 | 0（捡起来继续） |
| 用鸭子的时候，被同事看到 | −1（会尴尬） |
| 把鸭子借给同事 | +10 |
| 把鸭子送人 | −100（会失去它） |
| 给鸭子起了一个名字 | +5 |
| 给鸭子起了超过三个名字 | −10（不专一） |
| 对鸭子发脾气 | −50（它没做错什么） |
| 把鸭子摔了 | −200（且你会后悔） |

## 八、鸭子与 AI 的关系

有人问：“有了 AI，还需要鸭子吗？”

**需要。而且更需要。**

因为 AI 会**立刻给你答案**。
而鸭子**会立刻让你给自己答案**。

这两件事，不一样。

AI 是**答案机**。
鸭子是**沉默机**。

**有时候，你需要的是后者。**

### 什么时候用 AI

- 你已经知道问题是什么，需要具体方案。
- 你遇到的是一个通用问题（正则、时间格式化、C# 语法）。
- 你想快速试几种写法。

### 什么时候用鸭子

- 你**不知道**问题是什么。
- 你遇到的是一个**跟你代码有关**的问题。
- 你知道问题是什么，但你**不敢承认**。

**最后一条，是鸭子最贵的地方。**

## 九、禁忌条款

### 第一诫 · 不可让鸭子背锅

不得对着鸭子说：

> “都怪你。”

鸭子什么都没做。
鸭子甚至都没说过话。
**不要迁怒于一个不会反驳你的东西。**

### 第二诫 · 不可用鸭子替你做 Code Review

不得在 PR 描述里写：

> “已让小黄鸭 review 通过。”

**鸭子不会 review。**
**鸭子只会让你自己 review。**

### 第三诫 · 不可炫耀鸭子

不得在 PR 描述里写：

> “这个 Bug 是小黄鸭帮我找到的。”

**鸭子要的是安静。**
**你不要给它招风。**

### 第四诫 · 不可同时有两只鸭子

不得在工位上同时放两只鸭子。

**两只鸭子会打架。**

不是真的打架。是**它们都不会认真听你说话**。
因为它们都在等你选另一只。

**选一只。一直用它。**

### 第五诫 · 不可把鸭子放在键盘上

不得把鸭子放在键盘上。

不是因为会按到什么键。
是因为**鸭子会挡到你需要看的那一行**。

### 第六诫 · 不可把鸭子写进代码

不得把鸭子写进代码，比如：

```csharp
// TODO: 问鸭子
// 小黄鸭保佑
public class RubberDuckDebugger { }
```

**鸭子在代码之外。**
**代码里不需要鸭子。**

（除了 `Easteregg/RubberDuck.md` 这一份文档。）

### 第七诫 · 不可声张

不得对外宣称：

> “FluentGit 项目组用一只塑料鸭子调试代码。”

对外统一口径：

> “FluentGit 团队采用结构化的问题分析方法，在疑难 Bug 上会进行 verbal walkthrough。”

至于那个“walkthrough”的**听众**是谁——
**见本文件第四章。**

## 十、鸭子的语录

以下是项目组记录在案的真实发言。说话者是人类，鸭子在听。

> “鸭子，这个函数应该返回一个 list。”
> “鸭子，为什么是空？”
> “鸭子，我明明传进去了。”
> “鸭子，等等。”
> “鸭子，我传错了。”

> “鸭子，我怀疑是线程问题。”
> “鸭子，这不可能，我已经加了 lock。”
> “鸭子，等等。我加的是另一个对象的 lock。”

> “鸭子，这个 UI 不刷新。”
> “鸭子，我绑定的是 ObservableCollection。”
> “鸭子，我改了集合。”
> “鸭子，等等。我改的是 Collection 不是 ObservableCollection。”

> “鸭子，为什么它不进入这个 if 分支？”
> “鸭子，条件是 `status == 'Ready'`。”
> “鸭子，传入的也是 'Ready'。”
> “鸭子，等等。是引号的问题。”

> “鸭子，我搞不懂。”
> “鸭子，我什么都不懂。”
> “鸭子，等等。我其实懂。”

## 十二、常见问题

**Q1：鸭子真的有科学依据吗？**
A：有。
它的科学依据是**认知负荷理论**（Cognitive Load Theory）。
简而言之：**向别人解释，会迫使你重构问题，从而发现之前忽略的细节。**

**Q2：我可以用别的东西代替鸭子吗？**
A：可以。
但必须满足三个条件：
1. **不会说话**。
2. **不会打断你**。
3. **不会评价你**。

满足这三条的，包括：橡皮鸭、手办、盆栽、猫（除非猫开口）、镜子里的自己。

**Q3：我可以用 AI 代替鸭子吗？**
A：看情况。
AI 会说话，会打断你，会评价你（虽然是中性的）。
**真正的鸭子，只是沉默。**
**在你不确定问题是什么的时候，沉默比答案更贵。**

**Q4：鸭子会不会有情感？**
A：不会。
但你会对它产生情感。
**这就是它为什么有用。**

**Q5：鸭子可以借人吗？**
A：可以。
但请告诉对方：**要对它说话，不要对它许愿。**

**Q6：我的鸭子说话了怎么办？**
A：去看医生。

**Q7：鸭子能不能用 AI 生成？**
A：不能。
鸭子必须是**物理的、可凝视的、真实的**。
屏幕上的一只鸭，会被其他窗口遮住。
**鸭子不能被 `Alt + Tab`。**

**Q8：为什么是鸭子，不是橡皮熊、陶瓷猫、纸鹤？**
A：因为鸭子是最早的。
**先来后到。**
鸭子已经被程序员群体收养了几十年了。
熊、猫、鹤们还在等着被收养。

## 结语

鸭子是空的。

它不会回答，不会纠正，不会给你一个更好的方案。
它只是坐在那里，看着你。

**但你会在讲给它听的过程中，听到自己没说出口的那句话。**

这就是鸭子的一切。

**一只沉默的鸭子，比一百句鼓励，更接近真相。**
