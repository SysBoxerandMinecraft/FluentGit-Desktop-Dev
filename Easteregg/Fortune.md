
# 🎋 求签 · Fortune Draw

> “今天要不要重构？——问天。”
> “Should I refactor today? — Ask the heavens.”

英文版：[Fortune.en.md](./Fortune.en.md)

---

## 一、缘起

FluentGit 项目组有一种古老的决策方式。

不是开会。
不是投票。
不是 A/B test。

是**抽签**。

这个传统起源于一次架构争论。
两个人吵了两个小时：“该不该现在把 `GitService` 拆开？”
最后谁也没说服谁。

组里一个老工程师说了一句：

> “抽个签吧。”

抽签的结果是**上签**。
于是拆了。
拆完之后，还真的更清爽了。

**从那以后，凡是拿不定的技术决策，都会抽一次签。**

---

## 二、抽签的适用范围

签不是万能的。
签**只回答那些“你怎么决定都行”的问题**。

| 问题类型 | 能否抽签 | 原因 |
|---|:---:|---|
| 该不该现在重构？ | ✅ 可以 | 两种方案都能活，只是味道不同 |
| 该不该现在就发版？ | ❌ 不行 | 参见 [`Taboos.md`](./Taboos.md) 第一禁忌 |
| 该不该用 A 还是 B 库？ | ✅ 可以 | 两个库都靠谱，只是风格不同 |
| 该不该今天加班？ | ❌ 不行 | 答案永远是“不” |
| 该不该加这个功能？ | ⚠️ 谨慎 | 先看用户反馈，再抽签 |
| 该不该先修 Bug 还是先写文档？ | ✅ 可以 | 都行，看心情 |
| 该不该在周五部署？ | ❌ 不行 | 参见 [`Taboos.md`](./Taboos.md) |
| 该不该用 `async void`？ | ❌ 不行 | 答案永远是“不” |

**原则：**
**如果只有一个正确答案，不抽签。**
**如果有两个正确答案，才抽签。**

FluentGit 的签分为五等。每一等对应一个具体的开发决策。

### 3.1 上上签 · The Supreme

```text

║                                       ║
║           ✦  上 上 签  ✦             ║
║                                       ║
║        今 日 宜 大 动                      ║
║        一 动 千 秋                          ║
║                                       ║
║    所 求 皆 应 · 所 行 皆 通               ║
║                                       ║
╚═══════════════════════════════════════╝
```

**解读：**
今天是那种**十年一遇**的日子。
架构该怎么拆就怎么拆。
那个你拖了三个月的重构，今天做，会顺。
那个你一直不敢动的核心类，今天改，会有灵感。

**但注意：上上签只在极少数时候出现。**
**如果你一个月抽到五次上上签，说明你的签桶有问题。**

**行为建议：**
- 拆架构
- 重构核心模块
- 提一个大 PR
- 把 `Utils.cs` 彻底清掉

║                                       ║

**解读：**

如果你今天改代码，会引入 Bug。
如果你今天发版，会出事故。
如果你今天重构，会推倒重来三次。
如果你今天 push，会被 revert。

**这不是玄学。这是你自己的状态。**

**行为建议：**
- 请半天假
- 或者：只写文档，不写代码
- 或者：只 Review，不 commit
- 或者：看一遍 [`Incense.md`](./Incense.md)，重上一炷香
- **绝对不要**：
  - `git push --force`
  - 生产环境操作
  - 部署
  - 说“最后一个改动”

## 四、抽签代码

以下是 `FortuneService` 的最小实现。
请**严肃地**把它当作一份工程产物来读。

```csharp
using System;
using System.Security.Cryptography;

namespace FluentGit.Services;

/// <summary>
/// 求签服务。
/// 只做一件事：返回一个 Fortune。
/// 使用密码学安全随机数，因为决策不能作弊。
/// </summary>
public static class FortuneService
{
    private static readonly Fortune[] Pool =
    {
        // 权重与签等成正比。上上签稀少，是刻意的。
        Fortune.Supreme, Fortune.Supreme, Fortune.Supreme,

        Fortune.Auspicious, Fortune.Auspicious,
        Fortune.Auspicious, Fortune.Auspicious, Fortune.Auspicious,
        Fortune.Auspicious, Fortune.Auspicious, Fortune.Auspicious,
        Fortune.Auspicious, Fortune.Auspicious, Fortune.Auspicious,

        Fortune.Neutral, Fortune.Neutral, Fortune.Neutral, Fortune.Neutral,
        Fortune.Neutral, Fortune.Neutral, Fortune.Neutral, Fortune.Neutral,
        Fortune.Neutral, Fortune.Neutral, Fortune.Neutral, Fortune.Neutral,
        Fortune.Neutral, Fortune.Neutral, Fortune.Neutral, Fortune.Neutral,

        Fortune.Inauspicious, Fortune.Inauspicious, Fortune.Inauspicious,
        Fortune.Inauspicious, Fortune.Inauspicious, Fortune.Inauspicious,

        Fortune.Ominous, Fortune.Ominous
    };

    /// <summary>
    /// 求一签。
    /// </summary>
    public static Fortune Draw()
    {
        // 不使用 Random.Shared。
        // 求签不能是伪随机的。
        int index = RandomNumberGenerator.GetInt32(Pool.Length);
        return Pool[index];
    }

    /// <summary>
    /// 求一签，并把结果记录到日志。
    /// </summary>
    public static Fortune DrawAndLog()
    {
        var fortune = Draw();
        AppLogger.Info("Fortune", $"今日抽得：{fortune}");
        return fortune;
    }
}

public enum Fortune
{
    Supreme,       // 上上签
    Auspicious,    // 上签
    Neutral,       // 中签
    Inauspicious,  // 下签
    Ominous        // 下下签
}
```

### 关于随机数

**为什么用 `RandomNumberGenerator` 而不是 `Random.Shared`？**

因为 `Random.Shared` 是**伪随机**。
伪随机意味着：如果你知道种子，你就能预测结果。
如果签能被预测，那它就不叫签了。

**求签不能是伪随机的。**
**求签必须是真的不确定的。**

**这是唯一一个项目里强制使用密码学随机数的地方。**
**因为这是唯一一件不能作弊的事。**

## 五、抽签的规矩

### 5.1 一天只能抽一次

**每天早上上班时抽一次。**
抽完之后，**这一天就按这支签走**。

不能因为抽到下下签，就再抽一次。
不能因为抽到中签，觉得不够，再抽一次。
**一天一签。一签一天。**

### 5.2 抽完之后不能反悔

抽完之后，**必须按签行事**。

如果你抽到下签，但今天有个紧急 Bug 要修——
**那就修。**

下签的意思不是“不能修 Bug”。
下签的意思是“**今天不要做多余的事**”。
修 Bug 是必要的，不是多余的。

**签是指南，不是法律。**

### 5.3 签可以给别人看

抽到的签，可以在群里发。

但不是为了“我今天下下签，所以别找我”。
而是为了**让团队知道你今天的状态**。

**下下签不是请假条。**
**下下签是提醒。**

### 5.4 不能在同一个问题上重复抽

不能因为“第一次抽到中签不够爽”，就再抽一次。

**一次问题，一次抽签。**
**抽到中签，那就是中签。**

**重复抽签 = 心理上想要一个特定答案 = 你已经知道答案了。**

## 六、禁忌条款

### 第一诫 · 不可对下下签撒谎

不得在下下签的当天，跟同事说：

> “我今天上上签，状态很好。”

**不要骗同事。**
**也不要在下下签那天硬撑。**

### 第二诫 · 不可给签加权

不得修改 `FortuneService` 里的 `Pool` 数组，让上上签概率变高。

**签桶的质量，就是签桶的公平。**

### 第三诫 · 不可在签里加“复活甲”

不得添加 `Fortune.Retry`（“再来一次”签）。

**没有复活甲。**
**签是什么，就是什么。**

### 第四诫 · 不可用抽签替代决策

不得在技术选型时，把两个方案**完全押在抽签上**。

**抽签的作用是打破平局，不是替代思考。**

```text
❌ "用 SQLite 还是 LiteDB？抽个签吧。"
✅ "两个都调研过了，都能满足需求，都是成熟方案。抽个签吧。"
```

**没调研就抽签 = 偷懒，不是玄学。**

### 第五诫 · 不可让别人替你抽

不得让同事帮你抽签。

**签是给自己抽的。**
**让别人替你抽，就是你不想面对结果。**

### 第六诫 · 不可在抽签时作弊

不得：

- 看一眼签桶再抽
- 洗签的时候有意识地留下某支签
- 抽到不满意就再抽一次

**这些东西，签桶都知道。**
**下次它会给你下下签。**

### 第七诫 · 不可声张

不得对外宣称：

> “FluentGit 项目组用求签做技术决策。”

对外统一口径：

> “FluentGit 采用基于工程师经验的直觉决策法，用于处理方案对等的技术选型问题。”

至于那个“直觉”是什么——
**见本文件第三章。**

## 八、常见问题

**Q1：抽签真的有用吗？**
A：有用。
它的作用不是预测未来，而是**给你的决定一个外部理由**。

当你纠结“要不要现在重构”的时候，
你其实是在跟自己打架。
抽一支签，让第三个人（签）替你做决定。
**决定权转移了，你就轻松了。**

**Q2：为什么签分五等？**
A：因为**五等对应五种状态**。
如果只有上/下两等，太粗暴。
如果有十等，太复杂。
五等，是恰到好处。

**Q3：能不能用掷骰子代替抽签？**
A：不能。
**签有文化，骰子没有。**
骰子只产生数字，签产生**意义**。

**Q4：抽到下下签，今天还能写代码吗？**
A：能。
但**只写文档级别的代码**：

- 文档
- 注释
- 日志
- 配置
- 测试（如果是纯新增）

**不要写业务逻辑。**
**不要改核心代码。**

**Q5：抽到上上签，今天一定能做成吗？**
A：不能。
上上签只表示“今日顺遂”，不是“今日必胜”。
**你还是要动手。**

**Q6：如果一周五天全是下下签呢？**
A：那说明：

1. 你的状态持续不好，去看看医生。
2. 或者，你用的签桶有问题（理论上不可能）。
3. 或者，你需要真的休息几天。

**下下签连出三天，是一个信号。**

**Q7：我能不能自己做一个签桶？**
A：可以。
欢迎在 `Easteregg/` 下开一个 `PersonalFortune.md`。
但不要动这份文件。

**Q8：为什么求签服务要在 `Services/` 目录下？**
A：因为它是一个 **Service**。
它服务的是**决策**，不是娱乐。
**把它放在 `Services/`，是认真的。**

## 结语

求签不是迷信。

**求签是承认——有些决定，你怎么做都对，也怎么做都错。**
**不如交给一个不会说话的第三方。**

签桶里的签，是我们自己放的。
但抽出来的那支，是我们自己选的。

**我们不是求签在替我们决策。**
**我们是在求签替我们承担决策的重量。**

然后无论结果如何，
**第二天，继续抽。**
