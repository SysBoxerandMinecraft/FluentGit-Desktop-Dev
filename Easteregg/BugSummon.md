# 🔮 Bug 召唤阵 / 驱逐阵 · Bug Summoning & Banishing Circle

> “复现不了 Bug，是因为你没念对咒。”
> “If you cannot reproduce the bug, you have not recited the right incantation.”

英文版：[BugSummon.en.md](./BugSummon.en.md)

---

## 一、缘起

FluentGit 项目组有两条铁律：

1. **能复现的 Bug，才是 Bug。**
2. **复现不了的 Bug，是幽灵。**

幽灵很麻烦。
它不在你的机器上出现，只在用户的机器上出现。
它不在 Debug 里出现，只在 Release 里出现。
它不在你盯着屏幕的时候出现，只在你转身倒水的 0.5 秒里出现。

面对幽灵，有两种做法：

- **科学做法**：加日志、加埋点、加 trace，一路追踪，把它钉死。
- **玄学做法**：画召唤阵。

这份文档，两种都讲。

---

## 二、Bug 的三种形态

在讨论召唤阵之前，先要认识 Bug 的分类。

| 类型 | 特征 | 复现率 | 处理方式 |
|---|---|:---:|---|
| **常驻型** | 每次都能复现 | 100% | 正常 Debug |
| **条件型** | 满足某个条件才出现 | 30–70% | 加日志，逐步缩小条件 |
| **幽灵型** | 无法复现，只在别人的机器上 | 0% | **召唤阵** |

**幽灵型 Bug 是召唤阵存在的唯一理由。**

如果所有人都在自己的机器上复现不了，那就只能在**精神层面**逼近它。

### 3.2 阵的规格

| 项目 | 规格 |
|---|---|
| 素材 | 纯 ASCII，无 Unicode 依赖（框线除外） |
| 尺寸 | 41 列 × 22 行 |
| 放置位置 | `Debug` 输出窗口，或 `AppLogger.Error` 的第一行注释 |
| 激活条件 | 遇到无法复现的 Bug 时 |
| 持续时间 | 直到 Bug 复现为止。可能永远 |
| 副作用 | 无。但别盯着看太久 |

## 四、召唤仪式

### 4.1 准备工作

**在召唤之前，你必须做四件事。**

```text
[ ] 记录 Bug 报告全文（原文，不要转述）
[ ] 记录复现步骤（哪怕是"用户说随便点了几下"）
[ ] 收集环境信息（OS / .NET 版本 / 屏幕分辨率 / 语言）
[ ] 检查该用户是否真的在使用最新版本
```

**第四步最重要。**

**80% 的幽灵型 Bug，是因为用户在用旧版本。**

在你开始画召唤阵之前，先问一句：

> “你能确认你用的是 v1.0.0 吗？”

如果他说“应该是最新的”——**那就是问题所在。**

### 4.2 画阵

打开 `AppLogger`，在日志文件顶部，把第三章的召唤阵**完整复制**进去。
**不要省略任何一行。**

```csharp
namespace FluentGit.Services;

public static class AppLogger
{
    /*
     *                    ╔═══════════════════════════════╗
     *                    ║                               ║
     *                    ║        ☠  BUG  ☠             ║
     *                    ║                               ║
     *                    ║      ╱╲     ╱╲     ╱╲        ║
     *                    ...（略）
     *                    ╚═══════════════════════════════╝
     *
     *                          召   唤   阵
     *                        Summoning Circle
     *
     *                    〔 A 〕  Staging 环境
     *                    〔 B 〕  生产环境
     *                    ...
     */

    private const string TAG = "AppLogger";
    // ...
}
```

**为什么画在 Logger 里？**

因为 Logger 是**唯一**在所有环境下都会执行的地方。
Debug 里跑，Release 里也跑。
有 UI 也跑，没 UI 也跑。

**阵必须画在所有人都会经过的地方。**

### 4.3 填阵

打开召唤阵，把你**已知**的每一个环境变量，填进对应的位置：

```text
〔 A 〕  Staging 环境         → ✅ 已测试，无问题
〔 B 〕  生产环境             → ⚠️ 未测试
〔 C 〕  用户 A 的机器         → ❓ 未知
〔 D 〕  用户 B 的机器         → ❓ 未知
〔 E 〕  Windows 10 22H2      → ✅ 已测试
〔 F 〕  Windows 11 24H2      → ⚠️ 部分测试
〔 G 〕  无网络环境            → ❌ 未测试
〔 H 〕  低内存环境            → ❌ 未测试
〔 I 〕  跨时区场景            → ❌ 未测试
〔 J 〕  屏幕分辨率 800x600    → ❌ 未测试
```

**看见了吗？**

你没测试的那些格子，就是幽灵可能出现的位置。

**召唤阵不会替你修复 Bug。**
**它只会告诉你——你没测哪。**
**然后你就会去测。**

**这就是召唤阵的全部秘密。**

### 4.4 启动

当你完成画阵和填阵，在 `AppLogger.Error` 里加一行：

```csharp
AppLogger.Error(TAG, "召唤阵已就位。开始追踪幽灵。");
```

然后，**开始加日志**。

召唤阵不是终点。
**召唤阵是起点。**

## 五、驱逐阵

如果召唤阵是为了**找到** Bug，
那么驱逐阵就是为了**赶走** Bug。

### 5.1 标准驱逐阵（ASCII 版）

```text
                ╔═══════════════════════════════════════╗
                ║                                       ║
                ║              ✟  退  散  ✟            ║
                ║                                       ║
                ║         ～～～～～～～～～～～           ║
                ║        ～～～～～～～～～～～～         ║
                ║       ～～～～～～～～～～～～～        ║
                ║      ～～  ✦  BUG  ✦  ～～            ║
                ║     ～～～～～～～～～～～～～～         ║
                ║    ～～～～～～～～～～～～～～～        ║
                ║   ～～～～～～～～～～～～～～～～       ║
                ║                                       ║
                ║          从此处，退出本进程            ║
                ║         Leave this process, now        ║
                ║                                       ║
                ╚═══════════════════════════════════════╝

                            退  散  阵
                        Banishing Circle
```

### 5.2 驱逐阵的用法

**驱逐阵不能用在真 Bug 上。**
真 Bug 是问题，你要修它，不是赶它。

**驱逐阵用在这些地方：**

| 场景 | 是否适合驱逐 |
|---|:---:|
| 已知原因，已修复，等待验证 | ❌ 不适合（应该删掉 Bug 记录） |
| 第三方库的 Bug，无法修复 | ✅ 适合 |
| 一个只在你脑子里出现过的“疑似 Bug” | ✅ 适合 |
| 一个你查了三小时、决定不查的 Bug | ✅ 适合 |
| 一个用户说“偶尔会这样”，但你已经决定接受 | ✅ 适合 |

**驱逐阵的作用，是给“不修的 Bug”一个正式的、诚实的、可审计的归宿。**

## 六、把 Bug 封印在 `#if false`

如果 Bug 太大，无法在本次迭代修，又不能放着不管，
项目组有一个正式做法：**封印。**

```csharp
#if false
// ╔═══════════════════════════════════════════════════════════╗
// ║                  ✦  SEALED  ✦                             ║
// ║                                                           ║
// ║  Bug ID      : #742                                       ║
// ║  Title       : Mica 背景在 Win10 19045 上偶尔闪白           ║
// ║  Reproduce   : 无法稳定复现                                 ║
// ║  Environment : Win10 19045, 16GB RAM, 无独显                ║
// ║  Reported at : 2025-01-12                                  ║
// ║  Sealed at   : 2025-02-03                                  ║
// ║  Sealed by   : @username                                   ║
// ║  Reason      : 影响面小，优先级低于 v1.2 的 P0 问题         ║
// ║  Revisit at  : v1.3 或收到更多报告                           ║
// ║                                                           ║
// ║  ⚠️ 本代码块是封印，不是废弃。                              ║
// ║  ⚠️ 任何人不得删除，除非重新评估优先级。                    ║
// ╚═══════════════════════════════════════════════════════════╝

// 原始逻辑（暂被封印）：
// private void ApplyBackdrop() { ... }
#endif
```

### 封印的规矩

1. **必须带 Bug ID。** 没有 ID 的封印，会在半年后变成幽灵。
2. **必须写清复现条件。** 哪怕只有“偶尔”两个字，也要写上。
3. **必须写清谁封的。** 有问题找他。
4. **必须写清什么时候重看。** 通常是下一个大版本。
5. **必须注明“不得删除”。** 否则会有人当垃圾清理掉。

**封印不是逃避。封印是诚实。**

## 七、禁忌条款

### 第一诫 · 不可把真 Bug 送进驱逐阵

真 Bug 是问题，不是幽灵。
送它进驱逐阵，等于“假装没看见”。
**六个月后，它会带着三个兄弟回来。**

### 第二诫 · 不可把封印当坟墓

封印的代码，是**暂时**封存的。
`#if false` 不是注释，是**休眠**。

如果两年后你打开 `#if false`，里面还是原样——
**那说明封印失败了。**

### 第三诫 · 不可无 ID 地封印

任何封印必须带一个可追踪的 ID（issue 号 / Bug 号 / 内部编号）。
**没有 ID 的封印，是一个黑洞。**

### 第四诫 · 不可用召唤阵替代日志

召唤阵是**起点**，不是**终点**。
画完阵，就该去加日志、加埋点、加 trace。
**只在心里画阵的人，一年后还在查同一个 Bug。**

### 第五诫 · 不可在用户面前画阵

**召唤阵是内部仪式。**

不要在一个用户报错的 Issue 下面，贴一个召唤阵。
那不是在解决他的问题。那是在表演。

**对外统一口径：**

> “我们已经在复现环境中追踪此问题，感谢您的反馈。”

### 第六诫 · 不可跳过环境排查

**80% 的幽灵型 Bug，都是环境不一致。**

在你开始画召唤阵之前，先做一次环境对比：

```powershell
# 用户端需要提供的信息
$PSVersionTable
dotnet --list-sdks
dotnet --list-runtimes
[System.Environment]::OSVersion
Get-ComputerInfo | Select-Object OsName, OsVersion, CsTotalPhysicalMemory
```

**环境对了，Bug 就少一半。**

### 第七诫 · 不可声张

不得对外宣称：

> “FluentGit 项目组画召唤阵来查 Bug。”

对外统一口径：

> “FluentGit 采用系统化的环境矩阵测试方法，覆盖多版本、多分辨率、多语言场景。”

至于那份“环境矩阵”是什么——
**见本文件第三章。它确实是一张矩阵图。**

## 八、功德与回向

| 行为 | 功德 |
|---|---:|
| 完整画一次召唤阵 | −10（消耗心力） |
| 画完阵，补了日志 | +30 |
| 画完阵，发现是自己没测的环境 | +50 |
| 成功复现幽灵 Bug | +100 |
| 把不可复现的 Bug 正式封印（带 ID） | +20 |
| 把真 Bug 送进驱逐阵 | −100 |
| 无 ID 封印 | −50 |
| 在用户 Issue 里贴召唤阵 | −200 |
| 半年后重看封印，并作出决定 | +40 |
| 半年后重看封印，然后合上 | −20 |

### 回向

> 愿此召唤阵，
> 一炷找出原因，
> 一炷找出环境，
> 一炷找出自己漏掉的那一步。
>
> 愿你的 Bug，
> 要么被复现，要么被封印。
> 不要挂在半空，让人失眠。

## 九、常见问题

**Q1：召唤阵真的有用吗？**
A：有用。
不是因为它能改变什么，而是因为它逼你**把已知的环境一一列出来**。
**列出来之后，你会发现：原来我什么都没测。**

**Q2：我能不能跳过召唤阵，直接修？**
A：不能。
你连 Bug 是什么都不知道，修什么？

**Q3：我能不能把召唤阵画在 `README.md` 里？**
A：不行。
召唤阵是内部仪式，不是宣传材料。

**Q4：封印能持续多久？**
A：**一个大的版本周期。**
一个封印超过两个大版本，说明它不该被封印，该被实现或删除。

**Q5：如果我在封印里发现第二个 Bug 呢？**
A：**开新 issue。**
不要叠封印。叠封印 = 代码考古。

**Q6：召唤阵和驱逐阵能同时画吗？**
A：不行。
一个项目同时召唤和驱逐，说明团队内部对 Bug 的态度不统一。

**Q7：如果 Bug 一年都没复现，能自动关闭吗？**
A：不能自动关闭。
**但要标注“休眠”。**
休眠的 Bug 在半年后如果再次被报告，优先级会**加倍**。

**Q8：我能不能把这份文档发给用户看？**
A：可以。
但用户看完后，大概率不会再来报告 Bug。

## 结语

Bug 召唤阵和驱逐阵，都不是真的。

**但它们背后的那件事是真的：**

**我们不知道 Bug 在哪。**
**我们知道我们不知道。**
**所以我们开始一项一项地排除。**

**召唤阵，是一种诚实的姿态。**

画一个阵，把已知的写上去。
把未知的留下。
然后，一件一件去测。

**直到那个幽灵，从阵中露出它的脸。**
