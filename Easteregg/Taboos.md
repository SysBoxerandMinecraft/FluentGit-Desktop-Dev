## 三、十二禁忌详解

### 第一禁忌 · 不可周五下午部署

**典故**

2024 年某个周五下午 4:47，某人执行了 `dotnet publish -c Release`。
五分钟之后，MSIX 包上架。
七分钟之后，用户报错。
九分钟之后，所有人开始打电话。

**没有人能修。**

因为所有人都已经在回家的路上。

**正解**

```text
可以在周五做的：
  ✅ 写代码
  ✅ 写测试
  ✅ 写文档
  ✅ Code Review
  ✅ 计划下周一的工作

不可以在周五做的：
  ❌ git push --force
  ❌ dotnet publish
  ❌ 改生产配置
  ❌ 改数据库 schema
  ❌ 改 CI 脚本
  ❌ 发版本
```

**若已违**

1. 立即在群里承认。
2. 立即回滚。
3. 立即给同事道歉。
4. 下周一，重新执行 [`Incense.md`](./Incense.md) 中的三炷香流程。

### 第二禁忌 · 不可说“这次改动很小”

**典故**

一句话，五个字，加一个引号。
它曾经在项目里出现过七次。**七次全部变成大改动。**

最夸张的一次：一位同事说“这次就改一行代码”。
结果那一行是 `App.xaml.cs` 里的一行。
牵出了 MVVM 架构不完整的问题。
改了两周。

**正解**

不要用“大小”形容改动。
用**改动范围**形容：

```text
❌ "这次改动很小"
✅ "这次改动涉及 3 个文件，1 个接口，0 个数据库迁移"

❌ "应该很快就能改完"
✅ "预计 30 分钟，如果有意外，会提前同步"
```

**若已违**

如果你说了“这次改动很小”，并且它真的很大——
请你**主动**在群里说一句：

> “我之前低估了改动范围，实际比预想复杂。我来负责。”

功德 −100，但态度 +50。

### 第三禁忌 · 不可说“应该没问题”

**典故**

“应该没问题”是**所有事故的统一前奏**。

- “这个分支应该没问题。”——结果 conflict。
- “这个参数应该没问题。”——结果越界。
- “这个时间应该没问题。”——结果跨时区。
- “这个用户应该没问题。”——结果是个边界值。

**正解**

删掉“应该”。要么说“我测过”，要么说“我没测”。

```text
❌ "应该没问题"
✅ "我本地测过了，场景 A / B / C 通过"

❌ "可能没问题"
✅ "没测过。要不要现在一起过一遍？"
```

**若已违**

去把你说的那句话，改成一句**可验证的陈述**。

不能验证的自信，是代码界的空头支票。

---

### 第四禁忌 · 不可说“在我机器上是好的”

**典故**

这句话在程序员圈子里流传了三十年。
它是**跨平台软件工程的墓志铭**。

在 FluentGit 项目里，它出现在一次 Mica 背景渲染失败之后。
一位同事说：“我机器上是好的。”
其他人问：“你机器是 Windows 11 吗？”
那位同事沉默了。

**正解**

```text
❌ "在我机器上是好的"
✅ "我机器是 Windows 11 22H2，.NET 10.0.1。你的环境是什么？"

❌ "肯定是你环境问题"
✅ "先 diff 一下我们的环境变量和 SDK 版本"
```

“在我机器上是好的”这句话本身没有错。
**错的是你把它当结论，而不是起点。**

**若已违**

把这句话改成：

> “在我机器上是好的。我们来对比一下环境。”

加一句话，功德全回来。

---

### 第五禁忌 · 不可说“这是最后一个改动”

**典故**

这句话是一句**自我诅咒**。

说出口的那一刻，宇宙就会给你安排一个新的需求。
而且这个需求**必须**在发版前完成。

FluentGit 项目组内部已经把这句话列入了黑名单。
谁说了，谁就要在群里发红包。

**正解**

```text
❌ "最后一个改动，改完就发"
✅ "本次计划的改动全部完成。如有新增，重新评估时间。"

❌ "就这一个了"
✅ "接下来我要开始发版流程。"
```

**若已违**

如果你说了“最后一个改动”，而它**真的**是最后一个，
请你买一杯咖啡给下一个被这句话坑的人。

因为不是你，就是他。

### 第六禁忌 · 不可对共享分支 `--force` push

**典故**

`git push --force` 是一个**合法的、危险的、诱人的**命令。

它像一把上了膛的枪。
在你自己家里（自己的分支）用，可以。
在公共场合（`main` / `develop` / `release/*`）用，**不行**。

FluentGit 项目曾有人对 `main` force push。
五分钟之后，三个人的工作没了。
两个小时之后，从 reflog 里捞回来了。
**但那份心理阴影，至今没有完全恢复。**

**正解**

```bash
# 允许的
git push --force-with-lease origin my-feature-branch

# 绝对禁止的
git push --force origin main
git push --force origin develop
git push --force origin release/*
```

如果真的要改共享分支，用 `git revert`。
**Revert 是给别人看的。Force 是给自己爽的。**

**若已违**

如果你 force push 了共享分支：

1. 立刻在群里说。
2. 立刻发 reflog 恢复说明。
3. 主动请 Reviewer 检查有没有丢东西。
4. 以后在本地把 `--force` 从 alias 里删掉。

---

### 第七禁忌 · 不可在 deadline 前一天重构

**典故**

重构是一件好事。
**但在 deadline 前一天重构，是一场赌博。**

赌赢了，你是天才。
赌输了，你是那个“拖延了发版两周的人”。

FluentGit 项目组规定：
**Release 前 7 天内，只允许 Bug Fix，不允许 Refactor。**

**正解**

```text
可以在 deadline 前做的：
  ✅ 修 Bug
  ✅ 补测试
  ✅ 写文档
  ✅ 优化注释
  ✅ 调整日志

不可以在 deadline 前做的：
  ❌ 更换 DI 容器
  ❌ 更换 MVVM 框架
  ❌ 重命名核心类
  ❌ 拆分 GitService
  ❌ 把 async void 改成 async Task（除非有 Bug）
```

**若已违**

如果你在 deadline 前一天重构了，并且搞砸了：

**立刻 revert。**

不要试图“再改一点就好了”。
那就是第五禁忌。

---

### 第八禁忌 · 不可不读 diff 就 merge

**典故**

“LGTM” 是 Code Review 里最便宜的一句话。
**也是最贵的一句话。**

因为它曾经花掉 FluentGit 项目组一个周末。

某次 PR 有 47 个文件改动，Reviewer 只看了一眼标题，回了个 LGTM。
合并之后发现，其中一个文件把 `AppState.cs` 的初始化顺序改错了。
周五合并，周一才被发现。

**正解**

```text
Review 时的最低要求：
  [ ] 看过全部 diff
  [ ] 至少留一条 comment（可以只是"这里没问题，确认"）
  [ ] 本地拉下来跑过（至少 build 一次）
  [ ] 确认没有意外文件（bin/、obj/、日志、密钥）

Review 时的高级要求：
  [ ] 理解改动的意图
  [ ] 想过边界情况
  [ ] 想过回滚方案
```

**若已违**

如果你 LGTM 了一个你实际没看的 PR：

1. 去把它再看一遍。
2. 主动在评论里说：“补充一下我之前漏掉的 review。”
3. 下次不要再 LGTM。

**LGTM 这三个字母，要有分量。**

---

### 第九禁忌 · 不可把 TODO 当永久方案

**典故**

TODO 有三种命运：

1. **被实现** —— 少部分。
2. **被删除** —— 也算好结局。
3. **被遗忘** —— 大多数。

FluentGit 项目组曾清理过一批 TODO。
最老的一条写在项目创建的**第三天**：
`// TODO: 优化性能`

三年了。
没人知道要优化哪里。
没人敢删。
**它就那样挂着，像一根晾了三年的毛巾。**

**正解**

```csharp
// ❌ 不合格的 TODO
// TODO: 以后优化

// ❌ 不合格的 TODO
// TODO: 加测试

// ✅ 合格的 TODO
// TODO(@username): 当仓库数 > 5000 时，ReposPage 加载会卡 3 秒。
//                  计划 v1.3 用虚拟化列表替换（见 issue #142）。

// ✅ 合格的 TODO
// TODO(@username): 2025-Q2 前，将 GitService.Commit 从同步改为异步。
```

**合格的 TODO 需要：**
- 一个负责人（`@username`）
- 一个触发条件或时间
- 一个行动方案
- 最好有一个 issue 链接

**若已违**

如果你发现自己写了一个“三无”TODO：

**立刻补上或删掉。**

不补也不删的 TODO，不是 TODO。
是**精神污染**。

### 第十禁忌 · 不可在生产环境调试

**典故**

生产环境是一个**很危险的地方**。

它看起来和你的开发机一样：一个终端、一个 Git 仓库、一个 `dotnet`。
**但它的每一条命令，都是真的。**

FluentGit 项目组曾经有人在生产服务器上执行：

```bash
git checkout main && git pull
```

想“更新一下代码看看”。
结果拉下来的版本和当时的数据库 schema 不兼容。
服务挂了 20 分钟。

**正解**

```text
允许在生产做的：
  ✅ 查看日志
  ✅ 查看进程状态
  ✅ 查看磁盘空间
  ✅ 重启服务（如果是明确的操作）
  ✅ 执行已评审过的脚本

不允许在生产做的：
  ❌ git pull
  ❌ dotnet build
  ❌ 手工改配置
  ❌ 手工改数据库
  ❌ "试一下" 任何命令
```

**若已违**

如果你在生产环境按了 F5 / Enter / 回车：

**第一件事：停手。**

**第二件事：在群里说。**

**第三件事：写事故报告。**

不要试图自己“修回来”。
你在生产环境的每一次额外操作，**都是一次新的风险**。

---

### 第十一禁忌 · 不可在代码注释里 diss 前同事

**典故**

代码注释是永久性的。
**你的每一句抱怨，都会比你的在职时间长。**

FluentGit 项目曾经在某个 `Utils.cs` 里发现过一句：

```csharp
// 这什么破逻辑，写的人脑子有病吧
```

后来通过 git blame 定位到了原作者。
**那位原作者，现在正是这个项目的 Tech Lead。**

没有人说什么。
但那句注释被悄无声息地删掉了。

**正解**

代码注释是用来**解释代码**的，不是用来**评价人**的。

```csharp
// ❌ 不合格的注释
// 这什么破逻辑
// 谁写的，出来
// 别问我，我也不知道为什么这么写

// ✅ 合格的注释
// 这段逻辑是为了兼容 Win10 19045 上的一个 Mica 渲染 bug。
// 当 Mica 不可用时，需要手动设置 SystemBackdrop。
// 参见 issue #87。
```

**若已违**

如果你曾经在注释里 diss 过谁：

**去把注释改掉。**

不是因为怕被看到。
是因为**那本来就不是注释该干的事**。

---

### 第十二禁忌 · 不可在凌晨三点做重大决定

**典故**

凌晨三点，是一个**危险的时刻**。

在这个时间，你会觉得：

- “这个架构，不如推倒重来。”
- “其实我早就不想干了。”
- “不如把整个 Repo 换一种技术栈。”
- “Force push 一下会死吗？”

**会。**

FluentGit 项目组规定：
**凌晨 1 点之后，不允许执行任何 `git push --force`、`rm -rf`、或架构重构。**

**正解**

凌晨三点，只允许做三件事：

```text
1. 睡觉。
2. 睡觉。
3. 睡觉。

如果实在睡不着：
- 写日志
- 写 TODO
- 写"明天要做的事"清单

但不要：
- 写代码
- 改架构
- 发版
- 提 PR
- push 到远端
```

**若已违**

如果你在凌晨三点做了重大决定：

**第二天早上，重新评估一次。**

如果那时候你还觉得那个决定对——**再执行。**

如果那时候你觉得“昨晚怎么想的”——**恭喜，你正常了。**

## 四、禁忌之间的关系

十二条禁忌不是孤立的。

它们像一张网：
- 违反第五禁忌（“最后一个改动”）的人，往往也会违反第一禁忌（周五部署）。
- 违反第二禁忌（“改动很小”）的人，往往也会违反第七禁忌（deadline 前重构）。
- 违反第十禁忌（生产调试）的人，往往也违反了第八禁忌（没读 diff）。

**为什么？**

因为它们背后是**同一个心态**：

> “应该没事的。”

十二禁忌合起来，其实是**一条禁忌**：
**不要赌。**

## 六、常见问题

**Q1：这十二条是硬性规定吗？**
A：不是。它们是**共识**。
违反不会扣工资，但会被 Reviewer 记住。
**被记住，比被扣工资更麻烦。**

**Q2：如果老板要求我在周五下午发版呢？**
A：发。
但要先做三件事：
1. 老板签字（不是玩笑，书面）。
2. 全员知道。
3. 提前写好回滚方案。

**老板要求 = 老板负责。**

**Q3：如果我就违反了一条，会怎么样？**
A：不会有任何事。
**但你三个月后会在半夜醒来想起它。**

**Q4：如果同事违反了，我要当面指出来吗？**
A：私下说。
不要在群里 @ 他。
不要在大群里截图。
**禁忌是用来提醒的，不是用来羞辱的。**

**Q5：我可以加一条自己的禁忌吗？**
A：可以。
在 `Easteregg/` 下开一个 `PersonalTaboos.md`。
但不要动这个文件。

**Q6：如果我违反了，我能用功德抵消吗？**
A：不能。
功德可以抵扣，事故不能。
**代码不是银行，bug 不是贷款。**

**Q7：为什么没有“不可复制粘贴代码”这种禁忌？**
A：因为每个人都在复制粘贴。
包括写这份文档的人。
**禁忌要写给所有人，包括自己。**

**Q8：这十二条以后会加吗？**
A：会。
每发生一次事故，可能加一条。
**希望我们永远不需要加第十三条。**
